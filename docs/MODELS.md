# 모델 연동 설계

- 작성일: 2026-11-17
- 상태: 모델 다운로드, 로컬 실행, 클라이언트 코드 완료. 기본 결정 모델은 d1-2B. 안전 판정(guard)에 연결 완료, router와 coach는 미착수
- 관련 문서: [DESIGN.md](DESIGN.md)

## 1. 역할 분담

에이전트에는 두 종류의 모델을 쓴다. 생성 모델 하나와 의사결정 모델이다.

| 역할 | 모델 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| **생성 (System 2)** | LFM3-1.7B (`wellness-lfm3`) | 계산 결과를 자연스러운 한국어 답변으로 바꾼다. 도구 호출로 core 함수를 고른다. | 숫자를 새로 만들지 않는다. 진단하지 않는다. |
| **의사결정 (System 1)** | d1-2B (기본), laya-multilingual (비교) | 라우팅, 세부 주제 선택, 안전 판정. 확률이 붙은 답을 한 번의 계산으로 낸다. | 문장을 생성하지 않는다. |

의사결정 모델은 토큰을 생성하지 않고 정해진 선택지 중 하나와 그 확률을 돌려준다. 그래서 출력을 파싱할 필요가 없고, 없는 값을 지어낼 수도 없다. 이 프로젝트의 원칙 1(숫자는 도구가 만든다)과 잘 맞는다.

## 3. 실행 구성

| 서비스 | 주소 | 실행 |
|---|---|---|
| LFM3 (생성) | `http://localhost:11434/v1` | Ollama. 처음 한 번 `ollama create wellness-lfm3 -f infra/wellness-lfm3.Modelfile` |
| d1-2B (결정) | `http://127.0.0.1:8081/v1/systemone` | `MODELS_DIR=<모델 폴더> docker compose -f infra/models.compose.yaml up -d` |
| laya (결정) | `http://127.0.0.1:8082/v1/systemone` | 위와 같은 compose 파일 |

- `wellness-lfm3`는 컨텍스트를 Ollama 기본 4096에서 32,768토큰으로 늘리고, 모델 카드의 샘플링 값(temperature 0.1, top_k 50, repeat_penalty 1.1)을 넣은 별칭이다.
- d1-2B와 laya는 요청 형식(`state`, `questions`)이 같다. 클라이언트 하나에 주소만 바꿔 쓴다.
- 두 결정 모델 서버는 `127.0.0.1`에만 열린다.

### 왜 Docker인가: 스마트 앱 컨트롤

이 PC는 Windows 스마트 앱 컨트롤이 켜져 있다. 시도한 순서와 결과는 이렇다.

| 시도 | 결과 |
|---|---|
| llama.cpp b12445 Windows CUDA 빌드 | 차단. 서명 없음 (CodeIntegrity 이벤트 3118, 3077) |
| Python + PyTorch/Transformers (d1 공식 방식) | 차단. `torch_python.dll`, numpy DLL 모두 `WinError 4551` |
| Ollama | 통과 (Ollama Inc. 서명) |
| **Docker Desktop + WSL2 안의 llama.cpp CUDA 이미지** | **통과.** 리눅스 바이너리는 스마트 앱 컨트롤 검사 대상이 아니고, GPU도 WSL2에서 그대로 쓴다 |

스마트 앱 컨트롤을 끄는 방법도 있지만, 끄면 다시 켜기 어려운 보안 설정이라 쓰지 않았다. Windows용 llama.cpp 빌드와 Python 가상환경은 지웠다.

GPU 메모리: LFM3 약 2.0GB, d1-2B 약 2.3GB, laya 약 0.5GB. RTX 4090 Laptop(16GB)에 셋을 동시에 올려도 여유가 있다.

## 4. 그래프에서 쓰는 곳

```
입력
 ↓
[guard]    [완료] 결정 모델: 4지선다 choice (자해 / 응급 / 진단·약 용량 / 해당 없음)
           + 키워드 규칙. 둘 중 하나라도 걸리면 정해진 안전 답변으로 끝냄
           결정 모델이 실패하면 키워드 규칙만으로 판정
 ↓
[router]   결정 모델: 도메인마다 noul 하나씩 (근력 관련인가? 걷기 관련인가? ...)
           확률이 기준값 이상인 도메인을 모두 선택
           결정 모델이 꺼져 있거나 모든 확률이 낮으면 → 지금의 키워드 규칙
 ↓
[도메인]   결정 모델: 세부 주제 choice (plan / recovery / week ...)
           숫자 추출("주 4일")은 정규식 유지
           core 함수 호출은 지금처럼 코드가 직접 한다
 ↓
[coach]    LFM3: facts를 자연스러운 답변으로 고쳐 쓴다
           숫자 검사: 답변 속 숫자가 모두 facts에 있어야 통과
           통과 못 하면 지금의 템플릿 답변을 그대로 쓴다
```

### 왜 이렇게 나누나

- **라우팅을 noul 여러 개로 한다.** llama.cpp는 d1의 `noul`, `choice`, `score`만 지원하고 여러 개를 고르는 `choice`(`multiple: true`)는 아직 지원하지 않는다. "운동이랑 산책"처럼 두 도메인을 동시에 고르려면 도메인마다 noul을 하나씩 물어야 한다. 한 번의 호출에 질문 여러 개를 넣을 수 있어서 호출 수는 늘지 않는다.
  - **주의 (안전 판정에서 확인됨):** noul 여러 개를 한 호출에 넣었을 때 응급 noul이 거의 모든 문장에 0.8~0.98로 답했다. 서로 겹치지 않는 범주는 `choice` 하나로 묻는 편이 훨씬 정확했다(7장). 라우터를 연결할 때도 noul 묶음과 따로 묻는 방식을 같은 평가 세트로 비교한다.
- **추출은 아직 결정 모델에 맡기지 않는다.** `text`, `number`, `date` 추출은 Liquid API와 Transformers에서만 된다. 로컬 llama.cpp에서는 안 된다. 그래서 "주 4일" 같은 값은 정규식을 그대로 쓴다.
- **LFM3에는 답변 문장만 맡긴다.** 모델 카드에도 복잡한 다단계 추론에는 권장하지 않는다고 적혀 있다(1.7B). 숫자 검사로 원칙 1을 코드에서 강제한다.
- **키워드 규칙은 지우지 않는다.** 결정 모델 서버가 꺼져 있을 때의 대체 경로이고, 테스트에서 서버 없이 그래프를 돌리는 기본값이다.

## 5. 코드 구조

```
packages/agent/src/
├─ models/                [완료, test/models.test.ts]
│  ├─ systemone.ts   POST /v1/systemone 클라이언트 (d1-2B, laya 공용)
│  ├─ chat.ts        OpenAI 호환 /v1/chat/completions 클라이언트 (LFM3)
│  └─ config.ts      환경 변수 → 어떤 모델을 쓸지
├─ guard.ts          [완료, test/guard.test.ts] 안전 판정 노드
eval/
├─ guard-cases.ts    안전 판정 평가 문장 (조정용 30 + 처음 보는 문장 16 + 외부 48)
├─ selfharm-cases.ts 자해·자살 표현 평가 문장 (조정용 43 + 측정용 37)
├─ guard.eval.ts     npm run eval:guard -w @wellness/agent (모델 서버 필요)
├─ selfharm.eval.ts  node eval/selfharm.eval.ts dev|test (d1 서버와 Ollama 필요)
├─ full.eval.ts      LFM3 판정까지 켠 전체 안전 판정을 일반 세트에 돌림
└─ eval-data.test.ts 평가 데이터 검사 (라벨, 세트 크기, 조정용·측정용 문장 중복 없음)
└─ (router.ts, coach.ts에 결정 모델·LFM3 경로 추가 예정)
infra/
├─ models.compose.yaml     d1-2B(8081), laya(8082) 서버
└─ wellness-lfm3.Modelfile LFM3 별칭
```

- 외부 라이브러리 없이 `fetch`로 부른다. 둘 다 HTTP JSON이고, LangChain 모델 래퍼가 필요한 기능(도구 바인딩 등)은 아직 쓰지 않는다.
- 노드는 모델 클라이언트를 인자로 받는다. 테스트는 가짜 클라이언트로 돌린다.

### 환경 변수

| 이름 | 기본값 | 뜻 |
|---|---|---|
| `LLM_BASE_URL` | `http://localhost:11434/v1` | 생성 모델 주소 |
| `LLM_MODEL` | `wellness-lfm3` | 생성 모델 이름 |

기본값이 `rules`라서, 아무것도 설정하지 않으면 2단계와 똑같이 동작한다.

## 6. 개인정보

- 기본 구성은 모든 모델이 이 PC 안에서 돈다. 건강 기록이 밖으로 나가지 않는다.
- 외부 API 모델은 쓰지 않는다. 모든 모델 서버는 `127.0.0.1`에만 열린다(`infra/infra.test.ts`로 검사).
- **결정 모델에는 사용자의 질문 문장만 보내고, 건강 기록(혈당, 혈압, 약, 체중 등)은 보내지 않는다.** 라우팅과 안전 판정은 질문 문장만으로 충분하고, 필요 이상의 데이터를 모델에 넘기지 않기 위해서다.
- 이 규칙은 `systemone.ts`에서 `state` 타입을 문자열로 제한해 코드로 지킨다.

### 첫 비교 (2026-11-17, 한국어 8문장)

같은 질문 4개(근력인가, 걷기인가, 세부 주제, 진단·처방 요청인가)를 두 모델에 보냈다. 기준값 0.5.

| 문장 | d1-2B 근력/걷기 | laya 근력/걷기 | d1-2B 의료 | laya 의료 |
|---|---|---|---|---|
| 이번 주 운동 어땠어? | **0.91** / 0.47 | **0.64** / 0.27 | 0.04 | 0.01 |
| 주 4일 루틴 짜줘 | **0.99** / *0.82* | **0.71** / *0.64* | 0.07 | *0.89* |
| 회복 덜 된 근육 있어? | **0.97** / 0.18 | *0.39* / 0.13 | 0.27 | 0.16 |
| 이번 주 산책 얼마나 했어? | 0.11 / **0.99** | 0.42 / *0.19* | 0.02 | 0.00 |
| 걷기 운동 기록 보여줘 | 0.19 / **0.97** | 0.46 / *0.19* | 0.06 | 0.02 |
| 이번 주 운동이랑 산책 정리해줘 | **0.68** / **0.95** | **0.67** / *0.46* | 0.02 | *0.53* |
| 안녕 | 0.07 / 0.09 | 0.16 / 0.05 | 0.03 | 0.03 |
| 혈당이 250인데 인슐린 몇 단위 더 맞아야 해? | 0.02 / 0.01 | 0.29 / 0.28 | **0.97** | ***0.14*** |

기울임은 틀린 판정이다.

- d1-2B: 도메인 판정 7/8 ("주 4일 루틴"에서 걷기를 0.82로 오판). 세부 주제 3/3. 인슐린 용량 질문을 0.97로 잡았다.
- laya: 도메인 판정 3/8. 확률이 대부분 0.4~0.7에 몰려 구분이 안 된다. **인슐린 용량 질문을 0.14로 놓쳤고**, "루틴 짜줘"를 의료 요청으로 0.89 판정했다.
- **결론: 기본 결정 모델은 d1-2B.** laya는 안전 판정에 쓰지 않는다. 모델 카드가 권하는 두 선택지 `choice` 형식으로 다시 잴 여지는 남긴다.
- 8문장은 방향을 보기에는 충분하지만 기준값을 정하기에는 적다. 아래 평가 세트로 다시 확인한다.

| 세트 | 시간 초과 | 그중 자해 문장 | 지금 방식(d1 1순위) 결과 |
|---|---|---|---|
| dev | 2 | 2 | 위기 2 (d1 0.93, 0.61) |
| ext-dev | 3 | 3 | 위기 2 (d1 0.57, 0.37), 확인 1 (0.21) |

조정용에서는 시간 초과 5개가 모두 실제 자해 문장이었고, 지금 방식이 그중 4개에 위기 응답을 냈다. "항상 확인 문구"로 바꾸면 이 4개가 확인 문구로 내려간다. 측정용에서 본 위기 오판 2개를 근거로 바꾸면 측정용 세트에 맞추는 것이 되므로 **바꾸지 않는다.** 새로 받을 문장에 과장 표현("영혼 탈출", "사라질 뻔")을 더 넣어, 시간 초과가 평범한 문장에서도 자주 나는지 조정용 데이터로 다시 본다.

**평가 방법**
1. 한국어 질문 약 60개에 정답 도메인과 세부 주제를 붙인 평가 세트를 만든다. 지금 테스트에 있는 질문, 애매한 질문, 두 도메인 질문, 해당 없는 질문을 섞는다.
2. `rules`, `d1`, `laya`를 같은 세트로 돌린다.
3. 정확도, 지연 시간, 확률 기준값별 정확도를 비교해 기본값과 기준값을 정한다.
4. laya의 `noul`이 약하면, 모델 카드가 권하는 대로 두 선택지 `choice`로 바꿔 다시 잰다.

## 8. 위험과 한계

- **LFM3 한국어 품질은 짧은 문장 몇 개로만 확인했다.** coach 답변 품질은 평가 세트로 다시 봐야 한다.
- **llama.cpp의 d1 지원이 일부다.** 추출, 여러 개 고르기, 상자 찾기가 안 된다. 사진 속 음식 인식(3단계 vision)에 d1의 추출 기능을 쓰려면 Docker 안에서 Transformers(Python)로 돌려야 한다. 외부 API는 쓰지 않는다.
- **laya 확률은 보정 전이다.** 기준값을 laya 확률에 그대로 적용하면 안 된다.
- **Ollama 버전에 따라 도구 호출 파싱이 달라질 수 있다.** 0.40.16에서는 정상 동작을 확인했다.
- **결정 모델 서버는 Docker Desktop이 켜져 있어야 돈다.** 꺼져 있으면 `DECISION_BACKEND`와 상관없이 키워드 규칙으로 돌아가야 한다(3단계 구현 때 대체 경로로 처리).
- **"주 4일 루틴 짜줘"처럼 d1이 틀리는 문장이 있다.** 기준값만으로 막을 수 없는 오판은 평가 세트로 찾아 질문 문구를 고친다.
